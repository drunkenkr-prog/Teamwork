## 상세

### 1. 보내기 버튼 더블탭 = 중지 — 높음
- 근거: `send()` 591줄 `if(busy){ aborter?.abort('user'); return; }`. `setBusy(true)`가 첫 `await` 전에 동기로 실행되므로 두 번째 클릭은 100% "중지"로 해석된다. 하네스 11b는 Ctrl+Enter만 검사하고 버튼 연타는 안 본다(목이 즉답이라 봤어도 못 잡는다).
- 재현: 목 응답 지연 800ms, `#send` 두 번 클릭 → 카드 3장 모두 `중지했습니다.` (probe A).
- 영향: 모바일에서 더블탭·손떨림은 일상이다. 병렬이면 요청 3개, 토론이면 chain 전체가 죽고 로그에 오류 3건이 남는다. 사용자는 "가끔 앱이 답을 안 한다"로 인지한다. `CHECKLIST` 2번 "같은 버튼을 연타해도 요청이 두 번 나가지 않는다"는 통과하지만, **한 번도 안 나간다**.
- 제안(2번, 3줄): 전송 직후 700ms 동안 ■ 입력을 무시하거나, ■ 를 별도 버튼으로 분리. 하네스에 "지연 목 + 더블클릭 → 카드가 정상 채워짐" 검사 추가.

### 2. 저장 실패가 "저장했습니다"로 보인다 — 높음
- 근거: `store.set` 240~243줄은 실패 시 토스트를 띄우고 `storeBroken=true` 로 잠근다. 그런데 `saveSettings`(798줄)·`saveBoard`(748줄)는 `save()` 직후 자기 토스트 `'저장했습니다'` 를 띄워 **경고를 즉시 덮어쓴다**. 이후 `storeBroken` 잠금 때문에 `record()`의 저장 실패는 아무 표시도 없다.
- 재현: `localStorage.setItem` 을 QuotaExceeded 로 바꾼 뒤 설정에서 키 변경 → 토스트 `저장했습니다`; 보드 규칙 입력 → `저장했습니다`; 질문 전송 중 토스트 `저장했습니다` 그대로. 새로고침 → 키·규칙·대화 전부 소실 (probe D).
- 영향: 용량 한도(문제 4)에 닿는 순간부터 **API 키 변경·규칙 편집·모든 답변이 조용히 사라진다**. REVIEW 2-5 "처음 실패 시 토스트로 경고"는 코드상 참이지만 사용자에게는 안 보인다. 메모리 폴백(`mem`)은 `loadState` 가 localStorage 만 읽으므로 새로고침 후 아무 역할이 없다.
- 제안(2번, 30분): `store.set` 이 성공/실패를 반환하고 호출부가 그 값으로 토스트를 고른다. 실패 상태를 상단 strip 에 배지로 상시 표시. 실패 시 "오래된 대화 기록 정리" 버튼을 같은 토스트에 붙인다. 하네스에 setItem 실패 목 검사 추가.

### 3. 180초 타임아웃 × max_tokens 16000 × 스트리밍 없음 — 높음 (추정)
- 근거: `REQUEST_TIMEOUT_MS = 180000`(287줄), `max_tokens:16000`(445줄), 응답은 완료 후 한 번에 수신. 16000 토큰을 180초 안에 받으려면 **초당 89 토큰 이상**이 필요하다. Opus 급 모델의 비스트리밍 출력 속도는 통상 그보다 낮다(추정, 실키 미보유). 참조 문서도 Opus 5.5 는 "어려운 요청은 수 분이 걸릴 수 있으니 타임아웃·스트리밍을 계획하라"고 명시한다. 게다가 Opus 5.5 는 **사고(thinking)가 항상 켜져 있고 그 토큰이 `max_tokens` 안에서 소비**되므로 보이는 본문은 16000 보다 작다.
- 영향: `max_tokens` 를 4096→16000 으로 올린 이유(코드 답변 잘림 방지)가 무효가 된다. 약 10K 토큰 넘는 답은 3분 대기 → "응답 시간 초과" → **한 글자도 못 받고 출력 토큰 요금은 전액 청구**. 재시도해도 같은 길이면 같은 결과. 사용자는 이유를 모른다.
- 제안: (즉시, 1줄) Anthropic·OpenAI 는 타임아웃 600초로 상향, Gemini 는 180초 유지(벤더별 상수). (P1, 2-A) 스트리밍 도입 시 타임아웃을 "첫 바이트까지 60초 + 마지막 청크 이후 60초"로 바꾼다. 이의 절 참고.

### 4. localStorage 용량 산정 — 중간
- 측정(Chromium): 단일 키 최대 **5,234,375자**(한글·ASCII 동일, UTF-16 단위). Safari 도 약 5MB 급.
- 산술: 16000 토큰 답변 ≈ 한글 25K~ 코드 55K자. 프로젝트 하나의 로그 60개(답변 45개 × 평균 29K자)를 실제로 넣으니 **JSON 1.36M자**(probe F). 즉 무거운 프로젝트 **3~4개, 혹은 코드 위주 프로젝트 2개**면 한도다. 모든 프로젝트가 한 키(`aiteam.v1`)에 직렬화되므로 프로젝트를 나눠도 소용없다.
- 추가: `trimLog` 는 개수(60)만 자른다 — 용량 상한이 없다. `p.rules` 도 상한이 없다(15K자 규칙 → 모든 호출 프롬프트 15K자, probe I). 저장마다 전체 stringify 11ms + setItem 19ms 는 허용 범위.
- 제안(2번): (가) 프로젝트당 로그 **용량 상한**(예: 600K자) 추가, 초과 시 오래된 턴부터 삭제. (나) 프로젝트별 키 분리(`aiteam.p.<id>`)로 한 프로젝트가 다른 프로젝트 저장을 막지 않게. (다) 규칙 필드 8K자 상한 + 카운터. (라) 내보내기/가져오기(JSON 파일)는 백업이 아니라 **용량 탈출구**로도 필요하다 — 2-H 와 별개 P1.

### 5. 진행 중 프로젝트 전환 — 중간
- 근거: `switchTo()` 693줄이 `renderLog()` 로 피드를 통째로 다시 그린다. 대기 중 카드는 로그에 없으므로 사라지고, 나중에 온 답은 **분리된(detached) DOM** 에 채워진다.
- 재현: 응답 지연 중 P2 로 갔다가 P1 로 복귀 → 대기 카드 0개, 답 도착 후 화면 카드 0개, 저장은 됨 (probe B). P2 화면에서 버튼은 ■ 상태 → 누르면 P1 의 요청이 끊긴다.
- 영향: 사용자는 "답이 안 왔다"고 보고 다시 묻는다(비용 2배). 하네스 14번은 "엉뚱한 프로젝트에 저장/표시되지 않음"만 검사하고 **원래 프로젝트로 돌아왔을 때**는 안 본다.
- 제안(2번, 1시간): 전송 중인 프로젝트 id 를 기억해 `renderLog()` 가 그 프로젝트면 대기 카드를 다시 그리고, `fillCard` 는 현재 화면이 그 프로젝트일 때만 DOM 을 만진다(아니면 로그만). 다른 프로젝트에서는 ■ 대신 "P1 답변 대기 중" 표시.

### 6. 재시도 없음 — 중간
- 근거: `ask()` 474줄은 한 번 호출 후 바로 실패 처리. Anthropic 529(overloaded)·OpenAI 429·Gemini 429(무료 등급)는 흔하고 대부분 수십 초 안에 풀린다. Gemini 429 본문에는 `retryDelay:'41s'` 와 "Please retry in 41.3s" 가 들어 있는데(probe J) 그대로 문자열로 보여 주고 끝난다.
- 영향: 토론 모드에서 2단계(구현)가 529 를 맞으면 3단계·결론은 "(이 팀원은 참여하지 않았다)"를 받고 결론이 코드 없이 나온다(1번 보고 13 과 결합). 사용자는 4단계 전체를 다시 돌린다.
- 제안(2번, 20줄): `ask()` 에 429/5xx/네트워크 오류 1회 자동 재시도(지수 백오프 5~30초, `Retry-After`/`retryDelay` 있으면 그 값, 중지 신호 존중). 카드에 "재시도 중…" 표시. **2-C(카드별 다시 시도 버튼)보다 값싸고 효과가 크다** — 2-C 는 사람이 눌러야 하고 토론 chain 은 되돌릴 수 없다.

### 7. 렌더 성능 — 중간
- 측정: 로그 60개(답변 29K자, 코드블록 포함)에서 `renderLog()` **1,324ms**(헤드리스 Chromium, 모바일 뷰포트). `md()` 자체는 0.1ms 로 문제없고, 비용은 DOM 삽입·레이아웃이다. 중급 폰은 3~5배 느리다(추정) → 앱 시작(825줄)·프로젝트 전환·삭제·기록 지우기마다 3~6초 멈춤.
- 제안(2번): 최근 10턴만 먼저 그리고 위로 스크롤하면 이전 턴을 붙이는 방식(가상화까지는 불필요). `<pre>` 가 큰 카드는 `content-visibility:auto` 로 레이아웃 지연.

### 8. 로그 데이터 모델 — 중간 (2-B 선행)
- 근거: 로그 항목은 `{role, text, agent?, seq?, error?}` 뿐. **시각·턴 ID·모드가 없다.** 턴 경계는 "user 항목 다음부터 다음 user 까지"라는 순서에만 의존한다. 스키마 버전 필드도 없어 `aiteam.v1` 안에서 형태가 이미 두 번 바뀌었다(단일 프로젝트→복수, rules 추가).
- 영향: 2-B(최근 N턴)·1-J(직전 결론 포함)·2-C(항목 교체)·2-D(누적 사용량)가 모두 "어느 항목이 어느 턴인지"를 필요로 한다. 지금 착수하면 각자 순서 추론 코드를 따로 쓰게 된다. 절단(`trimLog`) 뒤 화면 20턴 ≠ 저장 19턴(probe H)도 같은 뿌리.
- 제안(2번, 1시간, **2-B 보다 먼저**): 항목에 `turn`(uid)·`ts`·`mode` 추가, `normalizeProject` 에서 구항목은 순서로 turn 을 부여. 최상위에 `v:2`. `trimLog` 후 `renderLog()` 호출.

### 10. 검증 코드 프롬프트의 실효성 — 중간
- 근거: `DEF_ROLES.anthropic`(283줄) "그 검증 코드를 함께 써라" — 이 콘솔은 코드를 실행하지 않고, 사용자가 Unity 에 붙여 넣어 돌리기 전까지 아무도 그 검증 코드를 보지 않는다. 결론 담당(기획)은 코드를 못 돌린다. 즉 "검증 코드"는 답변 길이만 늘린다(출력 토큰 = 비용, 문제 3 의 타임아웃도 앞당긴다).
- `REVIEW_NOTE`(502줄)는 `판매가 < 원가+수수료` 를 **하드코딩**한다. 보드 `규칙·수식` 필드에 "판매가 ≥ 원가 + 수수료 5% + 세금" 처럼 다른 식이 들어오면 프롬프트 안에 서로 다른 기준이 두 개 생긴다. 모델은 하나를 고르고 사용자는 어느 쪽을 따랐는지 모른다.
- `CALC_WORDS` 의 `fee` 는 "coffee"·"feed"에도 걸리지만 검수 지시가 하나 붙을 뿐이라 무해.
- 제안(1번 결정 + 2번 반영, 1-C·1-F 와 묶음): "검증 코드"를 **"테스트 벡터 표(입력 → 기대값)를 손으로 계산해 표로 보여라"** 로 바꾼다 — 이건 사람이 눈으로 검증 가능하고 짧다. `REVIEW_NOTE` 의 수식은 `p.rules` 가 있으면 "규칙·수식 필드를 기준으로" 로 치환, 없을 때만 기본식.

### 11. `md()` 경계 사례 — 낮음~중간
- 재현(probe G):
  - 미종료 코드펜스 → 코드가 `<p>` + `<br>` 로 평탄화, `line.trim()` 으로 **들여쓰기 소실**, 코드 안 `- ` 줄이 `<li>` 로. `max_tokens` 잘림은 거의 항상 코드 중간에서 일어나므로 **잘린 코드 답변은 예외 없이 이렇게 깨진다**(1-5·2번 "잘렸습니다" 안내와 함께 발생).
  - `` `a**b` 와 `c**d` `` → `<code>a<strong>b</code> … </strong>` 태그 교차(브라우저가 자동 복구하지만 스타일 번짐).
  - 표·번호 목록은 원문 그대로(2-E 알려짐). 링크는 `<a>` 를 만들지 않아 **지금은** `javascript:` 위험이 없다.
- `innerHTML` 삽입처 전수: `renderEmpty`(esc 이름)·`cardHTML`(esc seq, 상수 color)·`fillCard`(md/esc)·`renderLog`(esc)·`renderStrip`(esc 이름, 클램프된 숫자)·`renderProjects`/`renderTodos`(textContent). **속성에 사용자 텍스트가 들어가는 곳은 현재 없다** → `esc()` 가 따옴표를 안 바꿔도 오늘은 안전. 단 2-E 에서 `<a href="…">` 를 만드는 순간 `"` 미이스케이프가 바로 구멍이 된다.
- 제안(2번, 2-E 에 흡수): 미종료 펜스 자동 닫기, 인라인 코드를 플레이스홀더로 먼저 빼기, `esc()` 에 `"`·`'` 추가, 링크는 `https?:` 만 허용. 하네스에 위 4개 검사.

### 12. 모바일 실사용 — 낮음~중간 (추정)
- iOS 는 백그라운드 탭을 수십 초~수 분 뒤 종료·재적재한다. 복귀하면 `busy` 도 요청도 없고, 로그에는 **질문만 있고 답이 없는 턴**이 남는데 화면에는 오류 카드도 안내도 없다(정상 완료된 턴과 구별 불가). 스트리밍이 없어 부분 답도 없다.
- `apple-mobile-web-app-capable` 이 켜져 있다. 홈 화면 앱(standalone)에서 `prompt()`(이름 변경)·`confirm()`(삭제·기록 지우기)은 iOS 버전에 따라 동작이 불안정했던 이력이 있다(추정).
- `100dvh` + `overflow:hidden` 상태에서 iOS 키보드가 올라오면 레이아웃 뷰포트는 안 줄고 사파리가 문서를 스크롤한다 → 헤더가 밀려나고 토스트(`position:fixed`) 위치가 어긋난다(추정). `visualViewport` 이벤트로 composer 높이를 맞추는 게 정석.
- 제안(2번): 시작 시 마지막 턴이 답 없는 user 항목이면 "답변이 기록되지 않았습니다(앱이 중단됨) · 다시 보내기" 카드를 그린다(30분). 다이얼로그는 시트 안 인라인 입력으로 교체(2-H 와 별개). 키보드는 실기기 확인 후 판단.

### 13. OpenAI 출력 상한 없음 — 낮음
- 근거: `callOpenAI` 429줄 본문에 `max_completion_tokens` 없음. gpt-5.x 는 reasoning 토큰도 출력으로 과금되므로 한 요청의 비용·시간 상한이 없다. Anthropic 만 16000 으로 묶어 둔 비대칭.
- 제안(3-C 결과 후 2번): 벤더별 출력 상한을 설정 시트에 노출(기본 16000). Gemini 도 `generationConfig.maxOutputTokens` 동일.

### 14. 외부 CSS 렌더 차단 — 낮음
- 근거: 9·12줄 `<link rel="stylesheet">` 두 개(jsdelivr Pretendard, Google Fonts). `<head>` 의 스타일시트는 로드 완료(또는 실패)까지 첫 페인트를 막는다. 지하철·해외 로밍 같은 느린 회선에서 빈 화면 수 초. 오프라인이면 실패까지 대기.
- 제안(2번, 5분): `media="print" onload="this.media='all'"` 패턴 또는 `rel="preload"` + 시스템 폰트 폴백. 모바일 우선 앱이면 폰트를 로컬 폴백으로 두는 게 맞다.

## 0번·1번에 대한 이의

**① 2-A(스트리밍) P1 강등 — 조건부 반대.** 1번은 "체감 개선"이라 했고 0번이 받아들였지만, 구현 관점에서 스트리밍은 UX 가 아니라 **정확성·비용 문제**다: (a) 문제 3 — 비스트리밍 + 180초는 긴 답을 받을 수 없는 조합이고, 실패해도 요금은 나간다. (b) 잘못된 방향으로 가는 답을 보고 중지할 수 없어 출력 토큰을 끝까지 낸다. (c) iOS 백그라운드 종료 시 부분 답조차 없다. 다만 3사 SSE 파싱 + 하네스 목 교체는 하루 이상 걸린다. **타협안**: 지금 당장 벤더별 타임아웃 상향(1줄)을 P0 로 넣고, 2-A 는 P1 유지하되 2-B(대화 맥락) 다음이 아니라 **바로 뒤**에 둔다. 2-B 로 입력이 늘면 응답 시간도 늘어 문제 3 이 더 자주 터진다.

**② 2-G(자동 검수 파이프라인) P0 — 순서 반대.** CI 자체는 1시간짜리라 P0 라도 상관없지만, 문제 9 를 고치지 않은 하네스는 단언 없는 검사·즉답 목·날짜 의존 때문에 "초록"이 의미가 없고 3-A 를 반영하는 순간 이유 없이 빨개진다. **하네스 보강 → CI** 순서여야 한다. 그리고 하네스는 실키를 못 쓰므로 CI 초록은 "목에서 안 깨짐"일 뿐이라는 것을 TASKS 완료 조건에 명시해야 한다.

**③ 1-A/2-B(대화 맥락) — 동의하되 선행 조건 추가.** 핵심이라는 판단은 맞다. 구현 입장에서 추가하는 조건: (a) 문제 8 의 데이터 모델(턴 ID·시각·버전)을 먼저 넣지 않으면 2-B·1-J·2-C 가 각자 순서 추론 코드를 따로 갖게 된다. (b) 컨텍스트에 넣을 때 `error:true` 항목과 "_(잘렸습니다)_" 꼬리표는 제외해야 한다 — 지금 로그에는 오류 카드도 그대로 들어 있다. (c) 토큰 상한을 문자 수로 정할 때 코드 답변은 한글보다 토큰당 글자가 2~3배 많으므로 "6,000자"는 벤더·언어별로 편차가 크다. 문자 수보다 "최근 2턴 전체 + 그 이전은 질문만" 같은 구조 규칙이 예측 가능하다.

**④ 1-I(Opus 5.5 + 16000 토큰 비용) — 1번의 진단은 방향이 틀렸고, 0번의 "사용자 결정" 유보는 맞다.** 참조 문서 기준 `claude-opus-5-5` 는 입력 $4 / 출력 $20 per MTok 으로 **Sonnet 4.6($3/$15)보다 싸고** Sonnet 5.5($2/$10)의 2배다. 1번은 "입력 토큰 3만"을 근거로 들었는데 입력 3만 토큰은 $0.12 다. 비용의 주범은 **출력 + 항상 켜져 있는 사고(thinking) 토큰**이고(토론 1회 구현 단계 출력 6K ≈ $0.12), 이건 모델을 바꿔도 절반밖에 안 준다. 진짜 레버는 (a) `output_config.effort`(기본 `medium`, `low` 로 내리면 사고 토큰 감소 — 단 구형 모델명에는 400 이므로 5.x 계열일 때만 전송) (b) 스트리밍 + 중지 (c) 2-D 사용량 표시다. 즉 1-I 는 "모델 선택"이 아니라 **"effort·출력 상한 설정 노출"** 로 재정의해야 하고, 기본 모델은 Opus 5.5 유지가 맞다.

**⑤ REVIEW 2-5 "저장 실패 시 토스트로 경고 — 수정 완료"는 사실이 아니다** (문제 2). 코드는 경고를 띄우지만 다음 줄에서 덮인다. 하네스에 검사가 없어서 통과로 기록됐다. "재검수 통과(잔여 0건)"는 **하네스가 보는 범위 안에서 0건**으로 읽어야 한다.

**⑥ REVIEW 2-1 "180초 타임아웃"과 "max_tokens 16000 으로 상향"은 같은 검수 회차에서 서로 모순되는 결정이었다** (문제 3). 두 값을 함께 놓고 산술을 한 흔적이 없다.

동의하는 것: 1번 문제 1(규칙 필드)·2(자기 초안)·11(테스트 벡터)의 P0 승격, R2-1 단계별 타임아웃 격리, 3-1 모델 종료 표. 1번 문제 3(Gemini 그라운딩)에 구현 메모 하나: `tools:[{google_search:{}}]` 는 1줄이지만 응답의 `groundingMetadata.searchEntryPoint` 표시 의무와 추가 요금이 따르므로 3-B 결과 없이는 안 붙이는 게 맞다.
