## 상세

### 1. 고정 배경 지식(게임 규칙·핵심 수식·결정 사항)을 둘 곳이 없다 — 높음
- 근거: `contextBlock(p)` (index.html 약 468~482줄)이 넣는 필드는 이름·스택·진행률·지금 하는 일·다음 목표·남은 할 일·최근 질문 3개뿐. 모두 **상태**(status) 필드이고 **규칙**(spec) 필드가 없다.
- 영향: "수수료가 매입·매출 양쪽에 붙는가", "통화 단위·반올림 위치", "흥정 폭 상한" 같은 것을 질문마다 다시 써야 한다. 안 쓰면 세 팀원이 각자 다른 가정으로 답하고, 결론은 그 가정 차이를 모른 채 "채택"한다. 가격 로직 검증(d)은 이 규칙 없이는 시작이 안 된다.
- TASKS 1-A(최근 N턴 기억)와 다르다. 1-A는 **흘러가는 대화**, 이것은 **바뀌지 않는 사실**이다. 둘을 같은 토큰 예산에 넣으면 규칙이 잘려 나간다.
- 제안: 1번(기획)이 필드 스펙 → 2번(구현)이 보드에 추가. 필드: `게임 개요`(장르·핵심 루프 3줄), `규칙·수식`(자유 텍스트, 항상 프롬프트 맨 앞), `결정된 사항`(날짜·한 줄, 토론 결론에서 누적). 컨텍스트 순서는 규칙 → 결정 → 상태 → 최근 논의.

### 2. 결론 담당이 자기 초안을 못 본다 — 높음
- 근거: `send()` 토론 chain의 결론 단계 (약 627~632줄):
  ```js
  + (closer!=='openai' ? sec('기획 의견', got.openai) : '')
  ```
  API 호출은 매번 무상태(single user message)이므로, closer가 OpenAI이면 1단계에서 자기가 쓴 방향·구조를 결론 프롬프트에서 **전혀 못 본다**. 구현 팀원에게 "문제가 있으면 지적하라"고 시켜 놓고, 결론은 지적의 대상(초안) 없이 지적만 읽고 판정한다.
- 재현: 하네스 `finalPrompt`(qa.js 118줄 부근)를 출력하면 `[기획 의견]` 절이 없다.
- 영향: 결론이 구현·조사 의견의 요약으로 퇴화한다. 기획이 세운 우선순위와 이유가 결론에서 사라지므로 "설계 결정"(a) 품질이 매번 깎인다. 0번 1차 검수가 `undefined` 문자열만 보고 **내용 누락**은 못 본 사례.
- 제안: 2번이 조건 제거(자기 것도 `[기획 초안(1단계)]`로 넣기). 1줄 수정. 오늘 가능.

### 3. 조사 팀원이 실제로 최신 조사를 못 한다 — 높음
- 근거: `callGemini()` (약 434~450줄) 요청 본문에 `tools` 필드가 없다. 검색 그라운딩 없이 `generateContent`만 부르므로 답은 학습 데이터 기준이다. `DEF_ROLES.google`은 "최신 기술·에셋·플러그인 조사, 이름과 버전을 밝혀라"라고 시킨다.
- 영향: "최신"이라고 쓰여 있지만 검증 불가한 버전명·존재하지 않는 에셋 링크가 나올 수 있다. 사용자는 "조사 팀원"이라는 이름 때문에 이를 믿는다. 3-F(링크 검증 절차)는 증상 대응이고 원인은 여기다.
- 추정: Gemini API의 `tools:[{google_search:{}}]` 그라운딩이 3.5-flash에서도 유효한지는 3번이 확인해야 한다(2.x에서는 유효했음). 무료 등급 한도·추가 요금도 같이.
- 제안: 3번이 3-B에 "그라운딩 on/off와 근거 URL 출력 형식"을 포함. 안 되면 역할 지시문에서 "최신"이라는 약속을 빼고 "확인 날짜를 적어라"로 낮춰야 한다.

### 4. 역마진 검수가 실제로 도는 조건이 너무 좁다 — 높음
- 근거:
  - `REVIEW_NOTE`는 결론 단계 프롬프트에만 붙는다 (약 631줄). **병렬 모드에는 검수 단계가 없다.**
  - 결론 단계는 `active.length >= 2`일 때만 생성된다 (약 626줄). 키가 1개면 검수 없음.
  - 결론 담당은 기본적으로 기획(OpenAI)이다. `sysFor()`는 "네 담당 영역에 집중"이라 하고, 기획 역할에는 계산·코드 권한이 없다. 검수는 코드를 실행 못 하는 팀원이 텍스트를 읽는 것으로 끝난다.
  - 구현 역할 지시문에는 역마진 문구가 있지만 "검증 코드를 함께 써라"까지이고, 그 검증 코드를 누가 돌려 보는지는 없다.
- 영향: 1인 개발자가 가장 흔한 사용 방식(키 1~2개, 병렬 모드로 빠르게 물어보기)에서는 역마진 검수가 **한 번도 실행되지 않는다**. REVIEW.md "1-3 수정 완료"는 토론+2키 조건에서만 참이다.
- 제안: 1번이 결정, 2번이 구현. (가) 병렬 모드도 요청에 가격·수량·흥정 단어가 있으면 구현 팀원 프롬프트 끝에 REVIEW_NOTE를 붙인다. (나) 참여자 1명이어도 "자기 검수" 단계를 돌린다(같은 프롬프트가 아니라 검수 프롬프트이므로 "같은 답 두 번"이 아니다 — 이의 ①). (다) 검수 결과에 계산이 필요하면 결론 담당이 아니라 구현 팀원에게 되묻는 2차 호출을 허용한다.

### 5. REVIEW_NOTE와 CHECKLIST가 다르고, 게임에 맞지 않는다 — 중간
- 근거: `REVIEW_NOTE` = 역마진(판매가 < 원가+수수료)·경계값·단위·누락 4개. `CHECKLIST.md` "계산식·역마진" = 9개(할인 후 검사, 율 클램프, 반올림 한 곳, 매입가 변경 시 재검사, 흥정 AI 하한, 합계 일치, 마이너스 잔고·재고 …). 프롬프트는 사람용 체크리스트의 절반도 안 시킨다.
- 게임 특성상 빠진 것: 이 게임은 **매입 흥정**도 한다. 매입 쪽 역마진(매입가 > 예상 판매가 − 수수료 − 목표 마진)과 흥정 AI의 **양방향 한계선**이 REVIEW_NOTE·CHECKLIST 모두에 없다. 세금은 CHECKLIST에만 있고 REVIEW_NOTE엔 없다.
- 역할 충돌: REVIEW_NOTE "빠뜨린 항목이 있으면 보완하라" vs `sysFor()` "네 담당 영역에 집중". 기획이 결론에서 코드를 보완해야 하는 상황이면 둘 중 하나를 어긴다.
- 제안(1-C에 흡수): REVIEW_NOTE를 CHECKLIST 9항목 + 매입 상한·흥정 양방향 한계로 동기화하고, "보완하라"를 "미달 항목을 명시하고 누가 보완할지 지정하라"로 바꾼다.

### 6. 토론 순서: 조사가 구현 뒤 — 중간
- 근거: chain 순서 기획→구현→조사→결론 (약 616~624줄). 조사 프롬프트는 "앞선 의견을 보고 놓친 최신 기술·에셋·대안을 조사해 제시하라".
- 영향: 코드는 이미 3단계 전에 다 써졌다. 조사가 더 나은 라이브러리·에셋을 찾아도 코드를 다시 쓰는 단계가 없고, 결론 담당(기획)은 코드를 못 쓴다. 결국 결론은 "일단 지금 코드로 가고 나중에 검토" 식이 된다. 조사가 각주로 전락한다.
- 다만 순서가 항상 틀린 건 아니다. "이 코드 검증해줘"류(d)는 구현→조사(검증)가 맞고, "어떻게 만들까"류(a, c)는 조사→구현이 맞다.
- 제안: 1번이 결정. 기본값을 **기획→조사→구현→결론**으로 바꾸고(조사 프롬프트: "기획 방향에 필요한 기술·에셋·대안을 조사해 구현이 고를 수 있게 하라"), 요청에 코드 블록이 포함되면 지금 순서(검증 모드)를 유지하는 2분기가 단순하다.

### 7. 결론이 보드로 돌아오지 않는다 — 중간
- 근거: 결론 카드는 `record()`로 로그에만 남는다. 보드의 `next`·`todos`는 사용자가 손으로 다시 적어야 한다. `contextBlock`의 "최근 논의"는 **질문**만 넣고 결론은 안 넣는다. 즉 토론에서 가장 비싼 산출물(채택/폐기 결정, 다음 단계 3개)이 다음 질문의 컨텍스트에서 사라진다.
- 영향: 다음 질문에서 팀원들이 이미 폐기한 대안을 다시 제안한다. 사용자는 결론을 복사해 보드에 붙이는 수작업을 매번 한다.
- 제안: 1번 스펙 → 2번 구현. 결론 카드에 "보드에 반영" 버튼: 다음 단계 3개 → 할 일 추가, 채택 결정 → `결정된 사항`(문제 1의 필드)에 한 줄 누적. 1-A 스펙에 "직전 결론 1개는 항상 포함"을 넣는다.

### 8. 병렬 모드에서 팀원을 고를 수 없다 — 중간
- 근거: `active = Object.keys(AGENTS).filter(a => S.keys[a])` (약 596줄). 키가 있으면 무조건 셋 다 호출. `sysFor()`의 "네 담당 영역에 집중" 때문에 코드 질문을 받은 기획·조사는 "구현 팀원이 할 일"이라며 비켜 가거나 겉도는 답을 낸다.
- 영향: (b) 코드 받기가 목적일 때 답 1개를 위해 3개 비용·3개 스크롤. 사용자는 결국 기획·조사 키를 지우거나 카드 두 개를 무시하게 된다. 병렬 모드의 존재 이유("빠르게 세 시각")와 실제 사용(한 명에게 묻기)이 어긋난다.
- 제안: 1번 결정, 2번 구현. 입력창 앞 `@구현`/`@기획`/`@조사` 토글(다중 선택). 기본은 전체. 선택된 팀원만 `active`에 넣는다.

### 9. 역할↔벤더 고정 — 중간
- 근거: `AGENTS`·`CALL` 매핑이 1:1 고정. 기획=OpenAI, 구현=Anthropic, 조사=Google.
- 영향: 키가 하나뿐인 1인 개발자(현실적으로 흔함)는 토론 모드가 병렬 모드와 같아진다(결론 없음, 문제 4). 같은 벤더로 세 역할을 돌리는 것이 기술적으로 아무 문제 없는데 설계가 막는다.
- 제안: 1번 결정. 역할마다 "이 역할이 쓰는 키/모델" 선택을 두어 한 키로 세 역할을 돌릴 수 있게 한다. 설정 시트 구조 변경이므로 P1.

### 10. 기획 단계 프롬프트에 CHECKLIST 1번 항목이 없다 — 중간
- 근거: 기획 1단계 프롬프트는 "먼저 방향과 구조를 잡아라. 팀원들이 이어받을 수 있게 요점을 정리해라"뿐 (약 617줄). CHECKLIST 1번 첫 절(요청을 항목으로 쪼개고, 가정을 "가정:"으로 명시, 결정마다 이유)은 사람 팀장용으로만 존재하고 AI 기획에게는 안 시킨다.
- 영향: 요청 항목 분해가 없으니 결론의 "누락 확인"(REVIEW_NOTE 2번)이 대조할 목록이 없다. 누락 검수가 형식적이 된다.
- 제안(1-C에 흡수): 기획 단계 출력 형식 고정 — `요청 항목 목록 / 가정 / 방향 / 우선순위+이유`. 결론은 이 목록과 1:1 대조.

### 11. 가격 규칙 명세와 숫자 테스트 벡터가 없다 — 중간 (누락)
- 근거: REVIEW.md는 "가격 계산 코드가 없다"에서 멈췄다. TASKS 1-E는 "코드를 붙여 넣고 토론 1회"인데, 그 전에 **무엇이 맞는 값인지** 정한 문서가 저장소 어디에도 없다. CHECKLIST 9항목은 "실행해 본 결과로 체크"라고 하지만 실행할 입력값이 없다.
- 영향: 1-E를 시작해도 AI가 "역마진 없음"이라 하면 그게 맞는지 확인할 기준이 없다. 검수 대상 정의가 빠진 검수다.
- 제안: 1번이 `가격 규칙 명세 1장`(원가 정의, 수수료 적용 지점, 세금, 반올림 위치·단위, 흥정 폭 상한·하한, 재고·잔고 하한) + 테스트 벡터 표 6~8행(예: 원가 1000·수수료 5%·흥정 −10% → 판매 하한, 매입 흥정 +15% → 매입 상한, 수량 0, 음수, 소수, 오버플로)을 먼저 쓴다. 이 문서가 문제 1의 `규칙·수식` 필드 초기값이 된다. 1-E의 선행 과제.

### 12. 보드 필드 중 답변 품질에 기여 없는 것 — 낮음
- 근거: `contextBlock`의 "진행률: 40%"는 모델에게 행동 지침이 안 된다(90%면 다듬기 단계로 오해할 수도). 완료된 할 일은 빠지고(`filter(t=>!t.done)`) 남은 것만 들어가서, "이미 만든 것"을 모델이 모른다. "지금 하는 일"과 "최근 논의"가 자주 같은 내용.
- 제안: 진행률은 프롬프트에서 빼거나 "단계(프로토타입/알파/베타)"로 바꾼다. 완료 할 일 최근 5개를 "완료:"로 넣는다. 추정: 토큰 비용 대비 품질 이득은 크지 않으니 P2.

### 13. 구현 단계 실패 시 결론이 코드 없이 결정을 낸다 — 낮음
- 근거: 구현이 시간 초과·오류면 `got.anthropic=''` → 결론 프롬프트에 "(이 팀원은 참여하지 않았다)"가 들어가고 결론은 그대로 "채택/다음 단계 3개"를 낸다 (약 634~648줄).
- 영향: 코드 요청(b)에서 결론이 "구현 없이 진행"을 결정해 버린다. 사용자가 실패 카드를 놓치면 잘못된 다음 단계를 따른다.
- 제안(1-D에 흡수): 필수 단계(요청에 코드가 필요하면 구현)가 실패하면 결론 대신 "구현 미완 — 재시도 필요" 카드를 낸다.

## 0번 검수에 대한 이의

① **REVIEW 1-2 "참여자가 1명이면 결론 생략" — 동의하지 않음.** 결론 단계 프롬프트는 1단계와 다른 프롬프트(REVIEW_NOTE + 채택/폐기)다. "같은 답 두 번"이 아니라 "자기 검수"다. 생략하면 키 1개 사용자는 역마진 검수를 영영 못 받는다(문제 4). 검수 단계는 남기고 문구만 "네 답을 검수하라"로 바꾸는 게 맞다.

② **REVIEW 1-3 "수정 완료"는 과장.** REVIEW_NOTE 삽입은 토론 모드·2키 이상·비코더 결론자라는 조건에서만 돈다. "잔여 0건"은 코드 결함 기준이고, 검수 설계가 실효적인지는 확인되지 않았다. 최소한 "병렬 모드 미적용"을 남은 과제로 적었어야 한다.

③ **TASKS 우선순위.** 1-B(README, P0)와 2-A(스트리밍, P0)는 답변 **품질**을 바꾸지 않는다. 이 콘솔은 사용자 본인이 쓰는 도구라 README는 P1이면 충분하고, 스트리밍은 체감 개선이지만 결론이 틀리는 문제(문제 2·4·6)보다 앞설 이유가 없다. P0으로 올려야 할 것: 문제 1(규칙 필드), 문제 2(1줄 수정), 문제 11(명세·테스트 벡터, 1-E 선행).
